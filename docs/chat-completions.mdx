Send OpenAI-compatible requests to `POST /v1/chat/completions`. The key requires `ai.invoke`.

## Messages

Supported roles are `system`, `developer`, `user`, `assistant`, and `tool`. System and developer messages become Bedrock system blocks. Consecutive user or assistant messages are consolidated because Bedrock Converse expects alternating roles. Message content may be a string or an array of OpenAI content parts: text parts for every role, image parts for `user` and `tool` messages, and refusal parts for `assistant` messages.

```bash
curl https://gateway.example.com/v1/chat/completions \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-model-id",
    "messages": [
      {"role": "system", "content": "Be concise."},
      {"role": "user", "content": "Explain token caching."}
    ],
    "temperature": 0.2,
    "max_tokens": 400
  }'
```

Supported generation controls include `max_tokens`, `max_completion_tokens`, `max_output_tokens` (a gateway compatibility alias), `temperature`, `top_p`, and `stop`. Output limits are forwarded to Bedrock as `inferenceConfig.maxTokens` for both streaming and non-streaming requests, subject to the [reasoning restrictions below](#reasoning-effort). If multiple limits are sent, the first non-null value wins in this order: `max_completion_tokens`, `max_output_tokens`, `max_tokens`. Each supplied limit must be a positive integer; the effective limit cannot exceed the model's administrator-configured maximum. If no limit is provided, that configured maximum is used. Only `n: 1` is supported.

Invalid requests return an OpenAI-style error whose `param` names the offending field, for example `messages[2].content[1].image_url.url`.

## Streaming

Set `stream` to `true` to receive server-sent events:

```bash
curl -N https://gateway.example.com/v1/chat/completions \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-model-id",
    "stream": true,
    "messages": [{"role": "user", "content": "Write a short haiku."}]
  }'
```

Each `data:` event contains a `chat.completion.chunk`. The stream ends with:

```text
 data: [DONE]
```

The final JSON chunk includes usage when Bedrock reports it. The server sends heartbeat comments during quiet periods to keep intermediaries from closing a valid stream.

## Token usage and context

Both streamed and non-streamed responses report per-request OpenAI-compatible `usage`:

- `prompt_tokens` counts all input tokens, including cache reads and cache writes.
- `completion_tokens` counts generated tokens.
- `total_tokens` is their sum.
- When caching is used, `prompt_tokens_details.cached_tokens` identifies cache reads. The LiteLLM-compatible `prompt_tokens_details.cache_creation_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens` fields expose the cache breakdown. These counts are already included in `prompt_tokens`; do not add them again.

Bedrock reports uncached input and cached input separately. The gateway combines them for this API while preserving separate billing categories internally.

Clients own conversation history, tool results, and context resets. Use the latest model call's `prompt_tokens` to measure its input context, rather than summing usage across calls. Include the latest output or subsequent tool results in a local estimate when projecting the next request. `/v1/usage` reports account usage over a period; it is not a session context endpoint.

## Model aliases and app tiers

Administrators can expose a configured alias such as `claude-opus-max-thinking`, and map an app tier such as `chat-app-max` to it. Send either ID as `model`; no provider-specific options are needed:

```json
{
  "model": "chat-app-max",
  "messages": [{"role": "user", "content": "Solve this problem."}]
}
```

An alias always selects its upstream model. Its **Reasoning configured by** setting determines who controls reasoning:

- **Alias (pinned)** (`reasoningSource: "alias"`, the backward-compatible default) pins effort and thinking and overrides client `reasoning_effort` exactly as before.
- **Client (OpenAI options)** (`reasoningSource: "client"`) honors the supported OpenAI Chat Completions option `reasoning_effort` (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`) using the upstream model’s reasoning controls. If omitted, the upstream model’s configured default effort applies; if none is configured, its provider default applies. Stored alias thinking/effort fields are ignored in this mode.

App tier IDs inherit their mapped alias’s mode. For example, if `chat-app-max` maps to a client-configured alias:

```json
{
  "model": "chat-app-max",
  "reasoning_effort": "low",
  "messages": [{"role": "user", "content": "Solve this problem."}]
}
```

The playground shows the upstream model’s supported effort choices for client-configured aliases and app tiers; pinned aliases instead show read-only settings. Other supported generation controls still work subject to model restrictions. Ordinary request validation still applies. Non-streaming responses and streaming chunks retain the requested alias or tier ID. Pricing, output limits, cache settings and AWS region come from the upstream; usage reporting records that upstream model.

Use **Admin → Model aliases** to define presets, then **Admin → Apps** to create named apps with custom tiers and alias mappings. Remap a tier without changing client model IDs. Renaming an app or tier changes its public ID. `/v1/models` lists only enabled, valid targets; unmapped tiers and aliases whose upstream is disabled are unavailable. Pinned alias settings must be supported exactly: the UI does not offer thinking off on always-thinking models or effort levels the model cannot honor.

Native Bedrock endpoints also honor reasoning ownership: client-configured aliases and app tiers route to the upstream model without overriding caller-supplied native reasoning options. Pinned policies remain unchanged; pinned Invoke rewriting is supported for Anthropic models only.

## Reasoning effort

For a model with reasoning enabled by an administrator, set `reasoning_effort` to `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`. When a request omits it, the model's configured default effort (if any) applies; otherwise the model's own default behavior is used. For models without reasoning enabled, `reasoning_effort` is ignored.

```json
{
  "model": "global.anthropic.claude-opus-4-7",
  "reasoning_effort": "high",
  "messages": [{"role": "user", "content": "Solve the problem step by step."}]
}
```

The gateway translates the value for the model family on Bedrock:

| Model family | Bedrock request |
| --- | --- |
| Claude Opus 4.6 and Sonnet 4.6 or newer (including Opus 4.7/4.8 and Claude 5 models) | Adaptive thinking with `output_config.effort`. Effort shapes all output — thinking, text, and tool calls. |
| Claude Opus 4.5 | An extended-thinking token budget plus `output_config.effort` (the `effort-2025-11-24` beta is added automatically). |
| Claude Sonnet/Haiku 4.5, Opus 4.1, Claude 4, Claude 3.7 Sonnet | An extended-thinking token budget: 1,024 (`low`), 4,096 (`medium`), or 10,000 (`high`). The configured output limit must be larger than the budget. |
| Amazon Nova 2 | `reasoningConfig.maxReasoningEffort` (`low`, `medium`, `high`). |
| OpenAI gpt-oss | `reasoning_effort` (`low`, `medium`, `high`). |

- `minimal` behaves like `low`. A level the model does not support is lowered to the nearest supported level (for example `xhigh` becomes `high` on Claude Sonnet 4.6, which supports `low`, `medium`, `high`, and `max`), or raised when no lower level exists.
- `none` leaves reasoning off. On models that think by default and allow turning it off (Claude Opus 5 and Sonnet 5 use `thinking.type: "disabled"`, Claude Sonnet 5.5 uses `"between_tools"`), the gateway sends the model's off switch; always-thinking models such as Claude Opus 5.5 keep their default.
- Claude's thinking modes require default sampling, so the gateway omits `temperature` and `top_p` whenever it turns reasoning on for a Claude model. At `high` effort, Nova 2 also rejects `temperature`, `top_p`, and an output cap, so those are omitted for that request.
- Changing effort or thinking settings starts a new Anthropic prompt-cache prefix. Keep effort constant within a cached conversation.

Readable reasoning appears in the non-standard `reasoning_content` field: `choices[0].delta.reasoning_content` when streaming and `choices[0].message.reasoning_content` otherwise. The gateway requests summarized thinking on Claude models whose default is to omit thinking text. Adaptive models may skip thinking for simple prompts, in which case no reasoning is returned.

Discover which values a model accepts in the model catalog: the dashboard's model pricing page lists each model's effort levels.

## Image input

User messages can include images as `image_url` content parts. Send either a base64 data URL or a public `http(s)` URL:

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "What is shown in these images?"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0KGgo..."}},
    {"type": "image_url", "image_url": {"url": "https://example.com/photo.jpg"}}
  ]
}
```

- Supported formats are PNG, JPEG, GIF, and WebP. The gateway detects the format from the image bytes, so a mislabeled data URL (for example PNG bytes declared as `image/jpeg`) still works. Other formats, such as SVG or HEIC, are rejected with `invalid_image`.
- Bedrock limits each image to 3.75 MB and 8,000 × 8,000 pixels. Downscale large images before sending them.
- `detail` is accepted for compatibility and ignored; Bedrock has no equivalent.
- The model must support image input. Text-only models return a Bedrock validation error.

### Image URLs

The gateway downloads `http(s)` image URLs before calling Bedrock. To protect internal networks, downloads:

- only use the scheme's default port (80 or 443) and reject URLs containing credentials;
- only connect to public unicast addresses — private, loopback, link-local, carrier-grade NAT, and other special-purpose ranges are refused, including after DNS resolution and on every redirect (up to 3);
- time out after 10 seconds and stop at 3.75 MB;
- accept only responses whose bytes are PNG, JPEG, GIF, or WebP, regardless of the declared content type.

A request may reference up to 20 distinct image URLs. Download failures return `400` with code `invalid_image_url` and the offending `param`. Administrators can turn downloads off in **Admin → Brand & AWS → Inference**; requests with image URLs then fail with `remote_image_urls_disabled`, and clients must send data URLs instead.

### Images in tool results

As a gateway extension, a `tool` message may carry an array of text and image parts — for example a screenshot returned by a browser tool. The images are forwarded inside the Bedrock tool result:

```json
{
  "role": "tool",
  "tool_call_id": "call_1",
  "content": [
    {"type": "text", "text": "Captured the page"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0KGgo..."}}
  ]
}
```

## Optional conversation ID

Use the same opaque conversation ID on successive calls to help **managed prompt caching** retain the previous input boundary when a turn adds more than Claude's approximately 20-block cache lookback window. For Chat Completions, either of these body forms works:

```json
{ "conversation": "thread-123" }
```

```json
{ "conversation": { "id": "thread-123" } }
```

These examples show just the extra field; `model` and full `messages` are still required. This adopts the OpenAI Responses API's field shape, **not its server-side conversation-history semantics**, and remains a gateway extension to Chat Completions. It does not add a `/v1/responses` endpoint.

Alternatively, send `X-Conversation-ID: thread-123`. The header also works on all four native Bedrock endpoints (Anthropic bodies for Invoke), in streaming and non-streaming mode. The body alias is only for Chat Completions/the playground, not native provider request bodies. If both are supplied, their IDs must match; conflicts return `400` / `invalid_conversation_id`. A null body field is treated as absent.

```python
from uuid import uuid4
from openai import OpenAI

client = OpenAI(base_url="https://gateway.example.com/v1", api_key="YOUR_GATEWAY_KEY")
conversation_id = str(uuid4())  # Generate once per conversation, not once per call.
response = client.chat.completions.create(
    model="your-model-id",
    messages=history,  # Always include the complete history.
    extra_body={"conversation": conversation_id},  # Chat Completions SDK extension
    # Or: extra_headers={"X-Conversation-ID": conversation_id}
)
```

- IDs are case-sensitive, 1–128 characters, using only letters, digits, `.`, `_`, `:`, or `-`. A UUID is recommended. Empty/malformed IDs return `400` / `invalid_conversation_id`. Successful responses echo the effective ID in `X-Conversation-ID`, including when supplied only in the body.
- Keep `X-Request-ID` separate: it identifies one logical request for retry/billing, while `X-Conversation-ID` stays constant across turns. Do not reuse one request ID for the entire conversation.
- Clients still own and send all history. This identifier does **not** load messages, create a server-side conversation, or select a provider cache key. Neither form is included in the model prompt or forwarded upstream.
- With managed caching enabled, a matching previous input endpoint gets an extra checkpoint before the current endpoint, within the four-checkpoint budget. This is the previous **input** boundary, not the generated assistant response. The prior TTL is retained; enabling the header does not switch to one-hour caching.
- Tracking is isolated by authenticated user, credential, upstream model, region configuration, and provider format. Use the same credential for continuity; use a fresh conversation ID for a new independent branch. Shared system/tool prefix caching is not partitioned by this header.
- Only hashes, block coordinates, TTLs, and ownership/version metadata are stored in PostgreSQL, shared across replicas. Hints expire with their 5-minute or 1-hour TTL (measured from request preparation); expired rows are removed opportunistically in bounded batches. No raw conversation ID or prompt text is stored by this feature.
- Changed tools/system/history/options, context compaction, expiry, concurrent branches, or unavailable metadata storage can cause fallback to ordinary stateless checkpoints. Concurrent updates use compare-and-set; a late response cannot overwrite a newer stored version. Provider acceptance records a hint, not proof of a cache hit. Provider token thresholds and cache availability still apply.

Omit both forms for existing stateless behavior. With managed caching disabled, IDs are validated and echoed but no boundary state is read or written. Existing TTL defaults are documented under [Managed prompt caching](/docs/administration/models-and-aws#managed-prompt-caching).

## Safe retries

Supply a stable `X-Request-ID` for a logical request that may be retried after an uncertain client outcome. A settlement receipt makes charging exactly-once for that ID. See [Credits and usage](/docs/credits#exactly-once-request-ids).
