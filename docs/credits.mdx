Credits are denominated in USD and owned by users. Every model has separate prices per million input and output tokens, with optional prices for cache reads and 5-minute or 1-hour cache writes.

## Check a balance

```bash
curl https://gateway.example.com/v1/credits \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY"
```

```json
{
  "object": "credit_balance",
  "dashboard_url": "https://gateway.example.com/profile",
  "currency": "USD",
  "balance": 18.42,
  "monthly_allocation": 25
}
```

The key requires `credits.read`.

## Current-month usage summary

Use the native summary when a downstream application needs one request to render USD used, remaining credits, an authoritative top-up-inclusive budget percentage, request count, and token usage:

```bash
curl https://gateway.example.com/v1/usage \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY"
```

```json
{
  "object": "usage_summary",
  "dashboard_url": "https://gateway.example.com/profile",
  "currency": "USD",
  "period": {
    "start": "2025-03-01T00:00:00.000Z",
    "end": "2025-04-01T00:00:00.000Z",
    "timezone": "UTC"
  },
  "credits": {
    "used": 163.22,
    "balance": 86.78,
    "monthly_allocation": 150,
    "percent_used": 108.81333333333333
  },
  "observed_at": "2025-03-27T12:00:00.000Z",
  "budget": {
    "version": 1,
    "status": "available",
    "reason": null,
    "opening_balance": 150,
    "top_ups": 100,
    "adjustment_removals": 0,
    "reset_additions": 0,
    "reset_removals": 0,
    "net_funding": 100,
    "effective_budget": 250,
    "metered_spend": 163.22,
    "remaining": 86.78,
    "percent_used": 65.288
  },
  "requests": 42,
  "tokens": {
    "input": 12000,
    "output": 3400,
    "cache_read": 2100,
    "cache_write_5m": 500,
    "cache_write_1h": 200,
    "cache_write": 700,
    "total": 18200
  }
}
```

The period is the current UTC calendar month. `period.end` is exclusive. `credits.used` is the metered USD value charged during that period, while `credits.balance` is the current balance. `percent_used` is `used / monthly_allocation × 100`, is not capped at 100, and is `null` when the monthly allocation is zero. The token `total` includes input, output, cache-read, and cache-write tokens.

### Authoritative period budget

The additive `budget` object has `version: 1`, `status: "available" | "unavailable"`, and a nullable `reason`. Use `budget.percent_used` for a top-up-inclusive meter; the legacy `credits` fields above are unchanged and their percentage still uses the configured recurring allocation.

| Budget field | Meaning (USD, except percentage) |
| --- | --- |
| `opening_balance` | Sum of all ledger additions minus consumption before the UTC month starts: carry-in funds, not a fresh recurring grant. |
| `top_ups` | Current-month administrator additions, including initial administrator funding created within this month. |
| `adjustment_removals` | Current-month administrator removals, expressed positively. |
| `reset_additions` | Sum of positive current-month monthly-reset deltas. |
| `reset_removals` | Sum of negative current-month monthly-reset deltas, expressed positively. |
| `net_funding` | `top_ups - adjustment_removals + reset_additions - reset_removals`; can be negative. |
| `effective_budget` | `opening_balance + net_funding`. |
| `metered_spend` | Current-month charged inference usage (`usage`, `chat`, `api`, `embedding`), excluding funding events. |
| `remaining` | Current account balance; when available, exactly reconciles with `effective_budget - metered_spend` in database arithmetic. |
| `percent_used` | `metered_spend / effective_budget × 100`; uncapped, and `null` for a zero denominator or unavailable budget. Exhaustion of a positive budget is 100%. |

For example, $150 opening funds plus a $100 top-up gives a $250 budget. Spending $163.22 leaves $86.78 and uses **65.288%**, regardless of the current recurring allocation setting. Editing that setting mid-month changes the legacy allocation fields but grants no new funds. A reset **replaces** balance with the allocation rather than adding it: it can add or remove funds. All reset deltas, including repeated manual resets, are summed.

The top-level `observed_at` is the database `statement_timestamp()` labeling the single MVCC snapshot used to read both account and ledger. It is not a historical replay cutoff or a promise that later calls reproduce that state. A visible committed event timestamp later than this observation makes the budget unavailable; such events are not silently omitted.

Availability requires supported, valid events throughout the owner's complete ledger and exact numeric reconciliation of both all-time ledger balance and period funding less spend with the current account balance. There is no rounding tolerance. Missing ledger history or existing writer rounding drift fails closed; this endpoint neither repairs historical data nor changes settlement writers.

When unavailable, **all seven funding fields** (`opening_balance` through `effective_budget`) and `percent_used` are `null`. `metered_spend` and `remaining` still report independently known finite values, otherwise `null`. `reason` is one of:

- `unsupported_ledger_event`: an unsupported type or malformed credit amounts/directions anywhere in the ledger;
- `future_ledger_event`: a visible event timestamp is later than `observed_at`;
- `ledger_balance_mismatch`: exact reconciliation fails, opening balance is negative, or current balance is nonfinite;
- `invalid_amount`: an otherwise accepted amount cannot be represented as a finite response number.

Clients should show an unknown/unavailable budget, not zero or a fabricated percentage, when status is unavailable. An older API without `budget`, or an unsupported budget version, is also unknown. Do not reconstruct the denominator as spend plus balance or substitute the recurring allocation. See the strict `PeriodBudget` schema in the [OpenAPI specification](/api/openapi.json).

## Full report link

Both native responses include `dashboard_url`, an absolute URL built from the
configured public `BASE_URL` and `/profile`. Downstream apps can offer a
**View full usage** link without knowing the gateway's routes. This optional
metadata is an integration extension, not a standard OpenAI field.

The link opens the regular signed-in **Profile, API & usage** page, where the
user can review charts, models, and usage history. It contains no API key or
user identifier and does not sign the user in; the browser session determines
whose report is displayed. Clients must not forward API credentials to it.

The gateway returns machine-readable accounting values and ISO dates. Clients
are responsible for readable labels and localized amounts/dates, preserving the
UTC reporting boundaries and distinguishing current balance from monthly spend.

## LiteLLM-compatible daily activity

For integrations that already understand LiteLLM spend reporting, the gateway implements the core self-service daily activity contract:

```bash
curl "https://gateway.example.com/user/daily/activity?start_date=2025-03-20&end_date=2025-03-27" \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY"
```

Both dates are required `YYYY-MM-DD` UTC dates, are inclusive, and may span at most 366 days. The response contains descending `results` with LiteLLM-style `metrics`, breakdowns by model, the `bedrock` provider, and opaque API-key ID, plus aggregate `metadata` totals. Playground activity uses the synthetic key label `playground`.

This is a deliberately focused compatibility subset: LiteLLM-specific teams, model groups, endpoints, compression savings, success/failure counts, filters, and pagination are not exposed. The endpoint never accepts a target user ID and always reports only the owner of the presented inference key.

Both usage endpoints require `credits.read` and return `Cache-Control: no-store`. Spend, request counts, and token metrics count only inference ledger events; monthly resets and administrator adjustments are excluded from those metrics but included in the native summary's budget funding. Zero-priced model calls are still recorded with their request and token counts even though spend is zero.

## Request admission and settlement

- A user needs a positive balance when inference begins.
- Actual provider usage is priced after the response.
- The ledger records input, output, cache-read, cache-write, total cost, source, model, and request ID.
- A response can cost more than the balance that was available when it began. Settlement records a partial charge rather than making the ledger negative.
- A zero-priced model produces no debit.

An exhausted balance causes subsequent inference calls to return HTTP `402` with code `insufficient_credits`.

## Exactly-once request IDs

Send a stable `X-Request-ID` when an application may retry a completed request:

```bash
curl https://gateway.example.com/v1/chat/completions \
  -H "Authorization: Bearer $AI_GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-Request-ID: job-842-attempt-1" \
  -d '{"model":"your-model-id","messages":[{"role":"user","content":"Hello"}]}'
```

Request IDs may contain letters, numbers, `.`, `_`, `:`, and `-`, up to 128 characters. Settlement receipts prevent the same valid request ID from being charged twice.

<Warning>
  A repeated request ID protects credit settlement; it does not turn inference into a response cache. Avoid concurrently sending different logical requests with the same ID.
</Warning>

## Monthly allocations

Administrators can set `defaultMonthlyCredits` per user or apply the value to the union of selected groups. On the first day of each UTC month, the built-in scheduler resets users with a nonzero allocation to that amount. An administrator can also trigger a reset manually.

Users can review balance history, consumption, model mix, token details, and ledger events in **Profile, API & usage**.

In **Admin → Ledger**, consumption and request totals (including the user and model breakdowns) count only inference events. Administrator balance changes and monthly resets remain in the credit ledger and affect balances, but are not consumption or inference requests. The ledger’s **Deducted** column includes all balance reductions, including adjustments.
