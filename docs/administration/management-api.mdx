The stable management base is `/management/v1`. It covers users, groups, user inference keys, login providers, branding, inference settings, AWS configuration, models, usage, analytics (including [throughput statistics](/docs/administration/models-and-aws#throughput-and-bedrock-quotas) for Bedrock quota requests), management keys, and audit history. The [management CLI](/docs/administration/cli), `aigctl`, runs these operations from a terminal: inside the gateway container without a key, or anywhere with one.

## Create a management key

An enabled administrator creates keys in **Admin → Security**. Select only the scopes the automation needs, add an expiry when possible, and copy the one-time `aigm_` value. With cluster access, `aigctl` creates one from inside the gateway container:

```bash
kubectl -n ai-gateway exec deploy/ai-gateway-ai-gateway -- \
  aigctl management-keys create --name provisioning --scope 'users.*,api-keys.write' --expires 90d
```

Use the key as a bearer token:

```bash
curl https://gateway.example.com/management/v1/users \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY"
```

<Warning>
  Management keys are administrative credentials. They cannot invoke `/v1`, but a write-scoped key can change users, providers, model access, or secrets. Keep it in a secret manager and prefer short expirations.
</Warning>

## Scope families

| Resource | Read scope | Write scope |
| --- | --- | --- |
| Users | `users.read` | `users.write` |
| User inference keys | `api-keys.read` | `api-keys.write` |
| Groups | `groups.read` | `groups.write` |
| Authentication | `auth.read` | `auth.write` |
| Branding | `branding.read` | `branding.write` |
| AWS | `aws.read` | `aws.write` |
| Models, model aliases and apps | `models.read` | `models.write` |
| Settings | `settings.read` | `settings.write` |
| Management keys | `management-keys.read` | `management-keys.write` |

Usage and audit access use `usage.read` and `audit.read`.

## Provision a key for a user

An automation with `api-keys.write` can create an inference key for a specific user without impersonating that user. The plaintext `aig_` value is returned once; the database stores only its SHA-256 digest.

```bash
curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" \
  --header 'Content-Type: application/json' \
  --data '{"name":"opencode-workspaces","scopes":["ai.invoke","models.read","credits.read"],"replaceExisting":true}' \
  "https://gateway.example.com/management/v1/users/$USER_ID/api-keys"
```

`replaceExisting` revokes all same-named keys for that user before creating the replacement. This is intended for repeatable downstream credential provisioning: a rerun rotates the credential instead of leaving multiple active copies. List redacted key metadata with `GET /users/{id}/api-keys` and revoke a key with `DELETE /users/{id}/api-keys/{keyId}`.

The operation is audited as `api_key.provisioned`. Disabled users can receive a key, but authentication with that key remains blocked until the account is enabled. Account enablement controls both login and API access; valid keys with the required scopes and sufficient inference credits are still required.

Use `enabled` in user creation, updates, and group bulk-user updates to control account access. The former `apiEnabled` field is no longer part of the API contract; historical client payloads containing it do not control access. Update those clients to use `enabled` instead.

## Monthly credits and spend limits

User creation, updates (`PATCH /users/{id}`) and group bulk-user updates take three credit control fields next to `defaultMonthlyCredits`:

| Field | Values |
| --- | --- |
| `monthlyCreditMode` | `reset` (default): the monthly run sets the balance to `defaultMonthlyCredits`. `rollover`: it adds them to the balance |
| `rolloverCap` | Rollover only: the balance the monthly credits may bring the user up to, in USD; `null` for no cap |
| `monthlySpendLimit` | The most metered usage the user can be charged in a UTC month, in USD; `null` for no limit |

```bash
curl --fail-with-body --request PATCH \
  --header "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" \
  --header 'Content-Type: application/json' \
  --data '{"defaultMonthlyCredits":100,"monthlyCreditMode":"rollover","rolloverCap":600,"monthlySpendLimit":300}' \
  "https://gateway.example.com/management/v1/users/$USER_ID"
```

Users also include `monthlySpendRemaining`, what the limit leaves this month (`null` without a limit), and `monthlyCreditsAppliedAt`, when the monthly run last applied their monthly credits. Group members (`GET /groups/{id}`) include the three fields. `POST /users/monthly-reset` applies monthly credits now and returns `usersReset`, `usersRolledOver` and `usersSkipped`: rollover users who already received this month's credits are skipped. See [Monthly credits](/docs/credits#monthly-credits).

## Models, aliases and apps

The model catalog that API clients see at `/v1/models` has three collections, each with the same operations: list (`GET`), get (`GET /{id}`), create (`POST`), change the given fields (`PATCH /{id}`) and delete (`DELETE /{id}`). Reads need `models.read` and writes `models.write`. Changes apply to the next request.

| Collection | Entries |
| --- | --- |
| `/models` | Bedrock models with prices (USD per million tokens), limits, region and reasoning controls. `modelId` is the Bedrock model ID, inference profile ID or ARN, and also the model's public ID. |
| `/model-aliases` | Other public model IDs for a model (`upstreamModelId` is the model's `id`), with their own name and reasoning settings: `reasoningSource: "alias"` pins `thinking` and `effort`; `"client"` lets requests choose `reasoning_effort`. |
| `/model-apps` | Apps whose tiers are public model IDs `<app>-<tier>`, each mapped to an alias by `aliasId`, or unmapped (`null`). Tiers default to `min`, `low`, `medium`, `high` and `max`. |

Every entry includes `available`: whether `/v1/models` lists it, which needs it and everything it depends on to be enabled, an alias's settings to suit its model, and a tier to be mapped. App tiers have their own `available`.

```bash
MODEL_ID=$(curl --fail-with-body -sS -X POST \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" -H 'Content-Type: application/json' \
  -d '{"modelId":"us.anthropic.claude-opus-4-6-v1","name":"Claude Opus 4.6","inputPricePerMTok":5,"outputPricePerMTok":25,"thinking":true,"maxOutputTokens":128000}' \
  https://gateway.example.com/management/v1/models | jq -r .data.id)

ALIAS_ID=$(curl --fail-with-body -sS -X POST \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" -H 'Content-Type: application/json' \
  -d "{\"modelId\":\"claude-opus-max-thinking\",\"name\":\"Opus, max thinking\",\"upstreamModelId\":\"$MODEL_ID\",\"thinking\":true,\"effort\":\"max\"}" \
  https://gateway.example.com/management/v1/model-aliases | jq -r .data.id)

curl --fail-with-body -X POST \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" -H 'Content-Type: application/json' \
  -d "{\"name\":\"chat-app\",\"tiers\":[{\"name\":\"max\",\"aliasId\":\"$ALIAS_ID\"}]}" \
  https://gateway.example.com/management/v1/model-apps
```

`PATCH` takes only the fields to change, and an empty one changes nothing; `null` clears an optional model field (cache prices, `contextWindow`, `description`, `region` for the AWS default region, and `defaultReasoningEffort`), and an app's `tiers` replaces the whole list (tier names must be unique). Unknown fields are refused, naming them, so a misspelled field doesn't silently do nothing. The runtime OpenAPI document describes each request body.

Public model IDs are unique across models, aliases and app tiers, including disabled ones and unmapped tiers (`409 conflict`). A model that an alias uses and an alias that an app tier uses can't be deleted, and a model change that would make one of its aliases' pinned settings invalid is refused (`409`). Changes are audited as `model.*`, `alias.*` and `app.*` with the entry's public ID or name. `GET /models` has listed models since earlier releases; its entries now also include `available`.

## Analytics time ranges

Analytics use rolling windows ending at the time of the request, not the current calendar day, week, month, quarter, or year. The dashboard labels make these windows explicit; the API's `timeRange` values remain unchanged:

| `timeRange` | Dashboard label |
| --- | --- |
| `hour` | Last 60 minutes |
| `day` | Last 24 hours |
| `week` | Last 7 days |
| `month` | Last 30 days |
| `quarter` | Last 90 days |
| `year` | Last 365 days |

Each day in a rolling window is exactly 24 elapsed hours, including across daylight-saving transitions and leap years. `month`, `quarter`, and `year` now use fixed day counts rather than subtracting calendar months or years. Existing saved selections still work, but their start dates can differ from earlier releases. The separate **Interval** control only changes chart aggregation, not the selected window.

Analytics include usage up to the time of the request, including the current day and hour. Interval buckets are aligned to UTC, for example 1-day buckets start at 00:00 UTC, so a window's first and last buckets are usually partial: with **Last 7 days** and a 1-day interval, the first day counts only usage after the window starts and the last day only usage until the request. Earlier releases omitted usage that a background refresh had not yet processed, such as the current day's, and usually showed the window's first bucket as empty.

### Custom windows

For a precise window, send `start` and `end` instead of `timeRange` (or together with `timeRange=custom`). Each is an ISO 8601 date, read as 00:00 UTC, or a date and time with `Z` or a UTC offset; times without an offset are refused, because they would be read in the server's time zone. The window includes `start` and excludes `end`, so `start=2026-10-01&end=2026-11-01` is October in UTC, and spans 1 minute to 10 years. Percent-encode a `+` offset (`%2B02:00`): an unencoded `+` in a query string reads as a space.

```bash
curl "https://gateway.example.com/management/v1/analytics/consumed?start=2026-10-01T09:00:00Z&end=2026-10-15T17:00:00Z&bucketSize=1h" \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY"
```

A custom window allows every interval (`bucketSize`) that is no longer than the window and gives at most 400 buckets, and defaults to the one closest to about 24 buckets; the rolling ranges keep their fixed intervals. A custom window ending in the past counts only usage before its end, also in its last bucket. Its balance burn-down ends at the balance at the window's end, and throughput treats a last hour that the window cuts short as that many minutes. In the dashboards, choose **Custom range** under **Range** and enter **From** and **To** in your browser's time zone.

## Analytics for users and groups

Analytics cover all users unless a request selects some. `userId` and `groupId` can each be repeated, and together they select the union of those users and the current members of those groups; each user counts once, also when selected directly and through a group or through several groups. At most 100 IDs can be selected in one request.

```bash
curl "https://gateway.example.com/management/v1/analytics/model-summary?timeRange=month&groupId=$ENGINEERING&groupId=$SUPPORT&userId=$ALICE" \
  -H "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY"
```

`GET /analytics/users` lists the selected people, and `GET /analytics/groups` lists the selected groups, or with only `userId` the groups of those users, counting only the selected people's usage. Earlier releases accepted one `userId` or one `groupId` and refused both together. **Admin → Analytics** has the same selection as its **People** filter.

## Pagination and errors

Collection endpoints generally accept `limit` and `offset`. Limits are clamped to 1–100. `GET /users?search=` matches a case-insensitive part of the username, email or display name (earlier releases matched the email only). Management errors have a stable envelope:

```json
{
  "error": {
    "code": "validation_error",
    "message": "A description of the failure",
    "requestId": "b475..."
  }
}
```

Responses include `X-Request-ID`. Supply your own request ID when correlating an automation run with audit events.

## Revision-safe configuration

Mutable configuration resources expose a `revision`. Send the current revision with an update so stale clients cannot silently overwrite newer settings.

Branding (`/branding`) and inference settings (`/settings`) are stored together and share one revision, so re-read either document after updating the other. Inference settings are `remoteImageUrlsEnabled` (download `http(s)` image URLs) and `reasoningReplayEnabled` (send Claude's earlier reasoning back; turning it off deletes the stored reasoning). For example, to stop the gateway from downloading `http(s)` image URLs:

```bash
curl --request PUT \
  --header "Authorization: Bearer $AI_GATEWAY_MANAGEMENT_KEY" \
  --header 'Content-Type: application/json' \
  --data '{"revision": 4, "remoteImageUrlsEnabled": false}' \
  https://gateway.example.com/management/v1/settings
```

The change is audited as `settings.updated`.

Secret writes are explicit:

```json
{ "operation": "preserve" }
```

```json
{ "operation": "replace", "value": "new-secret" }
```

```json
{ "operation": "clear" }
```

Plaintext secrets are never returned.

## Runtime OpenAPI document

Every deployment serves its management specification at:

```text
https://gateway.example.com/management/v1/openapi.json
```

The runtime document is the source of truth for the management routes in your installed version.
