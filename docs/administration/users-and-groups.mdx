description: "Manage local accounts, membership, API access, credits, and monthly allocations."

Users own sessions, inference keys, credit balances, monthly allocations, and usage history. Groups organize membership, bulk operations, and reporting; credits remain user-owned.

## Local users

Administrators can create users with a username, email, role, initial password, starting balance, monthly allocation, and group membership. New users can be required to change their password on first login.

Account controls have distinct effects:

| Control | Effect |
| --- | --- |
| Account enabled | Allows login and API access with valid, appropriately scoped `aig_` keys |
| Role | Grants user or administrator dashboard permissions |
| Credit balance | Amount currently available for inference |
| Monthly credits | Balance assigned on the first day of each UTC month |

Account enablement is the single control for login and API access. API requests still require a valid key with the required scopes, and inference requires sufficient credits. Disabling an account invalidates sessions and blocks all of its inference keys. The control plane prevents deleting, disabling, or demoting the final enabled administrator.

OIDC-linked users use the same **Account enabled**, role, credit, and quota controls as local users. Disabling a user in AI Gateway blocks access even when the identity provider successfully authenticates them.

## Groups

Create groups under **Admin → Groups**, then add manual members with `owner`, `admin`, or `member` membership roles. These membership roles describe the group relationship; they do not grant system-administrator access.

OIDC authentication does not import identity-provider groups or create group memberships. Manage memberships in AI Gateway manually or through the management API.

## Bulk user controls

Select one or more groups and apply a change to the union of their members:

- Set a monthly allocation.
- Enable or disable accounts, controlling login and API access together.

A user in multiple selected groups is updated once.

## Analytics attribution

Current group analytics use current membership. A user in multiple groups contributes to each applicable group summary. Moving a user changes how historical usage appears in group-level views, while the underlying user-owned ledger remains unchanged.

## Analytics for selected people

The **People** filter on **Admin → Analytics** narrows the whole page to any users and groups you select, without visiting each user's page. Search by name, username, email or group name, and remove a selection with its badge or **Clear**. The selection covers the selected users together with the current members of the selected groups, each user once:

- The balance, credits consumed and tokens are the selection's totals, and the charts, throughput and model breakdown show only its usage.
- The per-user summary lists the selected people, so you can compare them.
- The per-group summary lists the selected groups, or the groups of the selected users when no group is selected, and counts only the selected people's usage.

The filter stays while the browser tab is open, also when you visit a user's page and come back. Together with **Range** and **Custom range**, it answers questions such as how much two teams used last month. The management API and `aigctl analytics` take the same selection: see [Analytics for users and groups](/docs/administration/management-api#analytics-for-users-and-groups).

## Monthly reset

The scheduler checks every minute and runs once on the first day of each UTC month. A PostgreSQL advisory lock and audit event make the reset safe when more than one application replica is running. Users with a monthly allocation of zero are skipped.
